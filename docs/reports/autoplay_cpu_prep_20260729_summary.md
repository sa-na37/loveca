# CPU対戦準備 オートプレイ再試行レポート 20260729

## 目的

次のゴールを「現行オートプレイモデルと2デッキ用UIを使ってCPU対戦できるところ」へ置くため、現行モデルのテストプレイ相当の試行を全デッキへ広げて確認した。

CPU対戦化では、以下が必要になる。

- 各プレイヤーのマリガン、ライブセット、メイン、効果選択を自動で決定する。
- 2デッキUIのフェイズ制御に、CPUが選んだ操作を順番に投入できる。
- ユーザーが見て理解できる行動ログと、モデル改善用の診断ログを分けて残す。

## 実施内容

- 全試行可能デッキに対して、4ターン・800試行のオートプレイレポートを再生成した。
- 2デッキ用の既存ルール/アダプタテストを実行した。
- 2デッキ埋め込みHTML生成が、1デッキHTML側のポーリング間隔変更に弱いことを確認し、固定文字列ではなく構造的にポーリングブロックを除去するよう修正した。

## 総評

現行モデルは、盤面コスト進行の大まかな推定には使える。特に `hit_rate` では多くのデッキがT4単独で0.6以上を出しており、ステージ継続モデルはCPU対戦の土台として残せる。

一方で、CPU対戦にそのまま使うには以下が不足している。

- ライブ成功目標が行動価値に十分入っていない。
- ライブセットが「手札交換」と「成功させるライブ選択」の二役を持つことをまだ分離しきれていない。
- 効果選択、pending解決、相手依存効果の自動判断が未整備。
- `combined_cumulative` はほぼ0に沈んでおり、盤面進行とライブスコア進行の両立モデルが未成熟。

## 観測した改善点

### 1. CPU対戦用には「ターン目標」だけでなく「操作候補」を返す必要がある

現行モデルは、試行内ではカードを選んでいるが、外部UIに渡せる形式の操作列を返していない。

CPU対戦接続では、最低限以下の形式が必要。

- mulligan: 戻す手札index
- live_set: セットする手札indexの配列
- main: プレイする手札index、配置先、起動効果の選択
- pending: 選択肢、対象カード、並び替え、Apply/Skip
- next: フェイズ進行

次の実装では、オートプレイを単なるレポート関数ではなく、`state -> action candidate` を返す決定器として切り出す必要がある。

### 2. ライブセット判断を3層に分ける必要がある

現行のライブセットは、低優先カードを交換して手札を掘る用途が強い。CPU対戦ではこれだけでは不足する。

分けるべき判断:

- 手札交換として捨てたいカード。
- 成功させたいライブカード。
- 後続ターンやエネルギーブーストのために温存したいライブカード。

特に `combined_cumulative` がほぼ0になっているのは、盤面進行とライブ成功計画がまだ同じ評価関数へ入っていないためと見てよい。

### 3. 盤面進行は「不足コスト」から改善できる

Miss Reasonsはかなり有用だった。

- 5軸/ポムポムミアSaint: T3 `11` 不足が主因。
- 10軸: T3 `10` 不足とT4 `15` 不足。
- 君ここ: T2 `7`、T3 `13`。
- 高コスト単騎系: T1/T2の中継カード不足より、T3以降の15+到達が主因。

CPU対戦の初期モデルでは、これをデッキ改造提案だけでなく、マリガン・ライブセット・ドロー効果選択の重みに戻すべき。

### 4. 2デッキUI基盤はおおむね使えるが、HTML変換の脆い箇所があった

2デッキテストは初回実行時に3件失敗した。

原因:

- 2デッキ埋め込みHTML生成が、1デッキHTML内の public polling block を完全固定文字列で探していた。
- 1デッキ側のポーリング間隔が `250` から `1200` に変更され、変換に失敗した。

対応:

- `llocg_dual_v2/server.py` で public view の `setInterval(refreshStateFromServer({force:false}), n)` を正規表現で検出し、間隔値に依存しない形で除去するよう修正した。

結果:

- `llocg_dual_v2` の72テストは再実行で全通過。

## CPU対戦実装への次ステップ

### Step A: CPU action policy adapter

既存オートプレイの評価関数を、2デッキUIへ送れる操作候補へ変換する小さなアダプタを作る。

- `MULLIGAN_*`: 戻す手札indexを返す。
- `LIVE_SET_*`: ライブセットindexを返す。
- `MAIN_*`: プレイ可能カードと配置先を返す。
- `PENDING`: まず安全な既定選択を返す。

20260729 追加:

- `suggest_autoplay_action()` を追加し、デッキリスト、カードDB、現在stateからCPU操作候補を返せるようにした。
- `AppState.autoplay_action_suggestion()` を追加し、アプリ側の正規デッキ読込経路から同じ候補を取得できるようにした。
- `/api/autoplay/suggest-action` を追加し、後続の2デッキUIからJSONでCPU候補を取得できる入口を作った。
- ライブセット選択は、試行用の手札交換処理から分離し、CPU候補では「選ぶだけ」の純粋な選択結果を使う。

現時点の対象:

- マリガン: T1-T3目標価値の低い手札indexを返す。
- ライブセット: 手札交換、ライブスコア目標、エネルギーブースト温存を加味して最大3枚のindexを返す。
- メイン: accepted targetのstage scoreを最も伸ばす1枚登場を返す。
- pending: 未対応pendingは先頭/既定選択を低信頼度で返す。

未対応:

- 起動効果の能動使用。
- 複数手順のメインフェイズ連続操作。
- コスト支払い、複数対象選択、並び替えの高度判断。
- 2デッキ中央UIからの「CPU操作を1手進める」ボタン接続。

### Step B: autoplay decision trace

CPUがなぜその操作を選んだかを記録する。

- 目標ターン形。
- 近い将来に必要なコスト。
- ライブスコア目標。
- 捨てた/温存した理由。
- 選択肢でApply/Skipした理由。

### Step C: 2デッキUIへのCPUモード追加

UI側には最初から完全自動ではなく、以下の段階で入れるのが安全。

- CPU提案だけ表示。
- 「CPU操作を1手進める」ボタン。
- 片側CPU。
- 両側CPU連続進行。

20260730 追加:

- `llocg_dual_v2/server.py` に `/cpu_suggest` と `/cpu_action` を追加した。
- `/cpu_suggest` は現在手番プレイヤーの非公開状態とデッキTSVを読み、`suggest_autoplay_action()` の結果を返す。
- `/cpu_action` は返された候補を、人間操作と同じ中央操作/プレイヤー操作経路へ流して1手だけ実行する。
- 2デッキ中央UIに `CPU 1手` ボタンを追加した。
- CPU用デッキ読み込みは、アプリ経由のruntime TSVと、`W42B` のようなDB内デッキコードの両方を探索する。

現時点の制限:

- 片側/両側をCPUとして固定する自動連続進行はブラウザUI側に入口を追加済み。
- pendingの高度判断はまだ低信頼度の既定選択であり、複雑な効果解決は今後の decision trace 強化対象。
- MAINでは現状1枚登場のみを1手として返し、複数手順のメインフェイズ展開はまだ連続化していない。

20260730 追加2:

- 2デッキ中央UIに `P1 CPU` / `P2 CPU` / `自動` トグルを追加した。
- CPU設定はブラウザの `localStorage` に保存し、再読込後も維持される。
- `自動` がonで、現在手番がCPU指定プレイヤーの場合、`/cpu_action` を1手ずつ順番に呼ぶ。
- 成功ライブカード選択など、人間の指定が必要な中央ポップアップが出ている間は自動操作を止める。
- 自動中も `/cpu_action` は既存の中央/プレイヤー操作経路を通るため、Undo履歴とフェイズガードは維持される。

20260730 追加3:

- アプリメニュー上の入口を `手動2デッキ対戦` / `CPUオート2デッキ` / `オートプレイ` の3系統に分離した。
- `/dual` は完全手動の既存2デッキシミュレータとして扱い、中央UIにCPU操作ボタンを表示しない。
- `/dual-cpu` は片側CPU/両側CPUを切り替えるCPU対戦用2デッキシミュレータとして扱い、起動時にCPU UIを有効化する。

- 今後のモデル改善では、このログを見ながら「なぜそのマリガン/ライブセット/登場/既定pendingを選んだか」を人間が追えるようにする。

20260730 追加6:

20260730 追加7:

- CPUのMAIN配置とUIなしオートプレイ試行から、ターン目標コストを上限として候補を捨てる処理を外した。
- これにより、ユーザー指定の「目標より大きいカードが最優先、目標ぴったりが次点、どちらもない場合は可能な限り大きく」という配置方針に揃えた。
- CPU判断ログの理由にも「目標超過を優先評価」したことを残す。
- これまで目標7-2の場面で13コストなどの上振れ到達カードを候補外にしていたため、CPU対戦/大量試行の達成率が実戦感覚より低く出る原因になっていた。

20260730 追加8:

- CPUのLIVE_SET判断ログに、ターンのライブスコア目標と実際に選んだライブカード番号・スコアを出すようにした。
- スコア目標カードを選択していた場合も、内部の「今回成功を狙うライブ」へ結び付いていなかったため、ログ信頼度や成功時効果近似が弱くなる可能性があった。これを共通のライブ選択関数側で修正した。
- 目標以上のライブスコアを達成候補として扱う方針は維持しつつ、CPU判断ログで追跡できるようにした。

20260730 追加9:

- CPUのMAINフェイズ終了判断を、単なる低信頼度Nextから `main_complete` / `main_pass` に分けた。
- 盤面がaccepted targetを満たしている場合は high confidence の `main_complete` として、達成した盤面コストと目標をログに残す。
- 改善候補がなく未達の場合は low confidence の `main_pass` として、現在盤面・最良目標・不足コストをログに残す。
- CPU自動は同じMAINフェイズ中でも1手ずつ再判断するため、改善候補がある限り `main_play` を返し、目標達成または手詰まりでNextへ進む。

### Step D: ライブ成功評価の強化

盤面コストだけでなく、以下を評価へ入れる。

- 要求ハート。
- エール期待値。
- ライブ成功時効果。
- 成功置き場の枚数と勝敗状況。
- 相手の成功見込み。

## 結論

次に実装すべきは、モデル自体の大改造ではなく、`state -> action candidate` のCPUアダプタである。
現行の盤面目標推論はCPUの「方針」として使えるが、2デッキUIへ接続するには、各フェイズで実際に押すボタン/選択肢を返す層が必要になる。

同時に、ライブスコアの連続達成が非常に低いため、CPU対戦として自然に見せるにはライブセット判断の強化を最優先にする。
