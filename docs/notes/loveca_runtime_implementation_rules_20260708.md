# Loveca runtime implementation rules 20260708

目的: LLCG simulator の runtime / UI / card effect 実装で、実装者ごとのばらつきとルール無視を防ぐための必須確認リスト。

この文書は `AGENTS.md` の補助ルールである。実装前・デバッグ対応前・完了前に必ず確認する。

## 実装前に必ず見るもの

1. `AGENTS.md`
2. この文書
3. 変更対象ファイルの `BUILD_TAG`
4. 既存の generic route / matcher / resolver / helper
5. 対象カードと同型効果の DB 効果文
6. 関連する既存デバッグコマンド

## 絶対に守る実装原則

- カード番号専用分岐を増やさない。
- 同型効果を拾える generic matcher / resolver に寄せる。
- 表示修正と効果処理修正を混ぜない。
- 既存 helper、常時 bonus 集計、pending 経路を落とさない。
- `engine_effect.py` に巨大な実装を戻さない。
- 新しい分割先を勝手に作らない。正式な分割先は `llocg_ui/effects/`。
- 実装済み確認カードを壊さない。

## UI / pending 必須ルール

- 自動効果は無言で処理しない。発生、条件達成/未達、解決結果が分かる pending / popup / log を残す。
- 効果の発生源を表示する。少なくとも `source_cn` と実行中効果の本文を pending に渡す。
- 確認ポップアップでは、実行中の効果だけを表示する。別効果の全文を混ぜない。
- 1候補しかない場合でも、原則として選択 UI を出す。
- 対象が存在しない場合も無言終了しない。条件未達または候補なしの確認表示を出す。
- 複数枚の手札コスト/対象選択は、可能な限り同時選択 UI にする。1枚ずつの連続選択は理由がある場合だけ。
- カード選択はカードリスト/画像リストで表示する。
- ポップアップ上でカードを指定する場合、カード番号だけの表示は禁止。
- メンバーカード表示は `Nコスト メンバー名`、ライブカード表示はカード名を基本にする。
- 枚数/人数/スコアなどの数値選択 UI では `0` / `1` / `2` をそのまま表示し、`0` を「使わない」、`1` を「使う」に変換しない。任意使用の yes/no UI と数値選択 UI を混同しない。
- heart / blade は共通 texticon / token renderer を使う。独自 glyph を増やさない。
- UI のバッジや overlay はウインドウサイズに依存して破綻しないよう、共通 renderer / responsive 表示へ寄せる。

## 公開 / 見る / エール表示ルール

- `公開する` と `見る` は公開範囲が違う。公開カードは public view / 公開領域にも反映する。
- 「公開されたカードの中から選ぶ」UI では、公開された全体と選択可能カードの違いが分かる表示にする。
- エール公開カードを使う効果は、どのカードが公開され、何枚が追加ドロー/追加エールに関わったかを表示する。
- 追加エールは、追加エールという事象が発生した直後に詳細確認できるようにする。
- ライブセット時ドロー位置に、確認したいエール公開カードを直接置かない。必要なら前置きダミーを使う。

## 条件 / タイミング / state ルール

- 条件達成/未達をログだけにしない。UI でも分かる形に寄せる。
- 「このターン」「このライブ中」「ライブ終了時まで」は state の寿命を明示して保存/リセットする。
- undo snapshot / restore に新規 state を入れる。
- ターン開始、ライブ開始、ライブ終了、リフレッシュ、成功ライブ置き場など、state のリセット地点を確認する。
- 発生源、最終情報、解決時参照が絡む場合は、誘発時固定か解決時参照かを確認してから実装する。
- バトンタッチ、エリア移動、登場元、公開カードなどの履歴は、汎用 ledger として記録し、カード個別 state にしない。

## 効果実装ルール

- まず DB 効果文を確認する。
- 同型カードを検索して、1枚専用実装になっていないか確認する。
- 既存 route に載せられる場合は拡張を優先する。
- 新規 matcher は文型名・効果 family 名で命名する。
- resolver は意味単位に置く。topdeck / energy / position / live_start / success_zone などに寄せる。
- 特殊分岐が必要な場合は、暫定 special と理由を残す。
- コスト処理と効果処理は分ける。任意コストは skip 可能 UI を明示する。
- エネルギー、手札、控え室、ステージ、成功ライブ置き場、メンバー下エネルギーを混同しない。
- 効果文が「カード」とだけ指定している場合、メンバー/ライブへ暗黙に絞らない。`メンバーカード` / `ライブカード` と明記されている場合だけ種類フィルタを付ける。

## デバッグコマンド必須ルール

- `AGENTS.md` の正本形式を使う。`DECK_CODE` wrapper は使わない。
- `!` を含むカード番号は bash の履歴展開を避けるため、環境変数では必ずシングルクォートする。
- 対象カードを即座にプレイ/起動/解決できる状態にする。
- 必要エネルギー、手札コスト、控え室対象、ステージ条件、成功置き場条件、山札上を不足なく入れる。
- 能力確認に不要な他誘発はできるだけ消す。
- BODY 常時は、すでにステージに置いた状態で開始する。
- LIVE限定 / MEMBER限定テストでは異種カードを混ぜ、フィルタ漏れを確認する。
- デッキ不足による不要リフレッシュを起こさない。必要なら十分な枚数を入れる。
- 成功ライブカード置き場に3枚以上置く初期状態は使わない。
- 実装した効果は、実行可能な個別起動コマンドまたは内部 smoke を `docs/debug/` に残す。

## 2デッキ対戦ルール注意

- ライブ勝敗判定でスコア同値の場合、8.4.6.2 により両方のプレイヤーがライブに勝利する。
- 8.4.7.1 の「両方のプレイヤーが勝利している場合、この時点で自身の成功ライブカード置き場にカードが2枚あるプレイヤーは成功ライブカード置き場へカードを移動しない」は、成功ライブカード置き場の枚数で判定する。現在のライブ置き場/ライブセット枚数で判定してはいけない。
- 1.2.1.2 の「両方のプレイヤーが同時に成功ライブ3枚以上なら引き分け」は保険として残す。ただし通常の 8.4.7 成功ライブ移動だけで、同値両者勝利から両者が同時に3枚目を置くケースを作らない。

## デバッグ対応時の扱い

- 未解決のユーザー/Codex コメントツリーは削除・上書きしない。ユーザーコメント `＊` は残し、Codex 側の追記は `※` で始める。
- `＊挙動問題なし` / `＊挙動確認済み` などで該当デバッグが完了した項目は、active command から外して `Resolved debug confirmations` へ移動する。
- 確認済み項目を移動するとき、重要な確認事項、再発防止ルール、汎用 UI/実装方針は消さない。`Resolved debug confirmations` の補足へ残すか、この文書へ一般化して移す。
- 未解決の指摘が同じツリーに残っている場合は active に残す。挙動確認済み部分だけを理由にツリー全体を resolved 扱いしない。
- ルール違反の指摘は、個別修正だけでなくこの文書へ一般化できるか確認する。
- 同じ指摘が2回以上出たら、共通 helper / renderer / pending template 化を検討する。
- `※YYYYMMDD内部確認` コメントは、デバッグ対応時の確認対象に含める。現行コードと矛盾する内容、検証条件不足、後続修正で壊れた可能性がある内容を見つけた場合は、必要な修正と再確認結果を追記する。
- 内部監査で問題なしの項目も、ユーザー確認が必要か再判定する。UI目視・操作感・ユーザー指定観点が残る場合は active/current に残し、内部整合だけで完了できる場合は監査済みリストへ移す。
