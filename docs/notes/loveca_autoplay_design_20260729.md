# Loveca Autoplay Design 20260729

## 目的

オートプレイは、デッキを自動で試行し、目標達成率と構築改善案を確認するための補助機能として実装する。
実装は3段階に分ける。

1. 汎用的なプレイ方針を導入したモデルの作成
2. 達成目標の設定によってモデルへ補正を加える機能
3. 繰り返し試行後、達成率を上げる構築改変を探索する機能

初期実装では、シミュレータの状態を直接進める前に、デッキリストからコスト進行テンプレートとの相性を評価する `stage1_policy_template` レポートを作る。

## 参考

- さーな「〖ラブカ〗コスト進行の基礎〜制限後の構築考察へ向けて〜」
- URL: https://note.com/sanapoke/n/n6d74b91d20db

参考記事から、序盤の代表的な進行をテンプレートとして採用する。

- `4 -> 9 -> 15単騎`
- `4 -> 7-2 -> 13-2`
- `4 -> 2-4-2 -> 2-10-2`
- `2-2 -> 2-4-2 -> 2-10-2`
- `2-2 -> 2-5-2 -> 2-11-2`
- `2-2 -> 2-7 -> 2-13-2`

## Stage 1: 汎用プレイ方針モデル

### 実装範囲

- デッキ内のメンバーコスト分布を集計する。
- デッキ内のライブスコア分布を集計する。
- 代表的なコスト進行テンプレートごとに、必要コストの充足度を評価する。
- 3ターン目までの進行を、5〜10コスト帯の厚みで補正する。
- 4ターン目以降の進行を、15コスト以上の厚みで補正する。
- コスト軽減や特殊なバトンタッチ形式を、カード番号専用ではなく効果文由来の汎用シグナルとして拾う。
- アプリメニューへ「オートプレイ」を追加し、デッキごとの方針レポートを表示する。
- モデルデッキ検証用に、人間可読のMarkdownレポートを出力できるようにする。

### 実装ファイル

- `loveca_app/autoplay.py`
  - オートプレイ用の副作用なしロジック。
  - `COST_PROGRESSIONS` に進行テンプレートを定義。
  - `build_autoplay_deck_report()` でデッキレポートを生成。
- `loveca_app/core.py`
  - `AppState.autoplay_deck_report()` でデッキ読込、検証、レポート生成を接続。
- `loveca_app/web.py`
  - `/autoplay` 画面を追加。
  - ホームメニューにオートプレイ入口を追加。
- `loveca_autoplay_report.py`
  - 指定デッキまたは全試行可能デッキの方針レポートを `docs/reports/autoplay/` へ出力。

### 現時点の評価仕様

- 各テンプレートの必要コストを集計し、必要枚数に対する採用枚数で充足度を出す。
- 目安として、各必要コストは「必要回数 x 3枚」程度あると安定寄りに評価する。
- `2-2` 進行は序盤の盤面スタッツを作りやすい前提で軽いボーナスを入れる。
- 5〜10コスト帯は3ターン目までの中継安定性として加点する。
- 15コスト以上は4ターン目以降の勝ち筋再現性として加点する。
- 効果文にコスト軽減系の語があるカードは、通常より高コスト接続しやすいシグナルとして扱う。
- 効果文にバトンタッチがあり、かつ高コスト寄りのカードは、特殊バトンタッチ進行のシグナルとして扱う。
- 2ターン目までのプレイ枚数が多い進行は手札消費リスクとして軽い減点を入れる。
- この評価はプレイング実行ではなく、方針候補を並べるための初期モデルである。

### モデルデッキ用レポート出力

```bash
cd /Users/tekitou/Desktop/gsim/loveca

python3 ./loveca_autoplay_report.py --deck user_data/decks/deck_sample.tsv
python3 ./loveca_autoplay_report.py --all

出力先:

```

モデルデッキを複数受け取った場合は、この出力を比較して、どの型が高く評価されるか、人間の想定とズレているかを確認する。

### 試行モデル 20260729a

`stage1_policy_template` の評価結果を使い、構築内容から到達したい各ターンの盤面コスト形を推定する簡易試行モデルを追加した。

方針:

- 3ターン目までは、推奨された序盤コスト進行を目標形にする。
- 4ターン目以降は、15コスト以上や特殊バトンタッチのシグナルを含む後半進行を優先する。
- 各試行では初期手札6枚から開始し、2ターン目以降に1枚ずつドローする。
- 各ターン、手札内で目標形に最も近いメンバー組み合わせを選ぶ。
- 完全一致率、平均ステージコスト、よく出た進行、サンプル進行をレポートへ出す。

この段階では、実シミュレータ engine を直接進行させる完全オートプレイではない。構築から見た「目標形への到達しやすさ」を粗く比較するためのドライランである。

実行例:

```bash
cd /Users/tekitou/Desktop/gsim/loveca

python3 ./loveca_autoplay_report.py --recent 3 --trials 500 --seed 29 --turns 4 --outdir docs/reports/autoplay
```

次段階では、ここで選んだプレイ方針を実 engine の選択処理へ渡し、実際のドロー、プレイ、効果処理、ライブ成否まで含めた試行へ拡張する。

### 試行モデル補正 20260729b

初回試行で不足していた以下を補正した。

- マリガンを明示的に試行へ入れる。
  - 序盤目標形に必要な2コスト、中継コスト、ドロー/エネルギーブースト系ライブを残し、残りを引き直す簡易方針。
- 達成判定を完全一致から上振れ許容へ変更する。
  - 例: `2-10-2` 目標に対する `2-11-2` や `2-13-2` は達成扱い。
  - 例: `2-7` 目標に対する `7-2-2` は達成扱い。
- 山を掘るライブ成功時ドロー効果を、手札改善として近似する。
  - 例: `君のこころは輝いてるかい？` の2ドロー1捨ては、ターン終了時に追加で山を見て手札を整える処理として扱う。
- 低コストを追加登場させる効果を、コスト進行判定上の追加2コストとして近似する。
  - 例: 7コスト矢澤にこの登場時効果によるコスト2以下メンバー追加。
- Daydream Mermaid 系のエネルギーブーストライブを、5軸ミラステの `2-4-2 -> 2-11-2` 進行に反映する。
  - `2-5-2` 目標に対して、T2に `2-4-2` を作り、Daydream Mermaid を成功できる手札がある場合は橋渡し成功として扱う。
- 特殊バトンタッチ検出を修正する。
  - `バトンタッチして登場した場合` のような受け身条件だけを持つカードは、特殊バトンタッチ札として扱わない。

まだ近似であり、ライブ成功率、必要ハート、相手スコア、控え室形成の厳密な再現は次段階の実 engine 接続で扱う。

### 試行モデル補正 20260729c

追加確認で、目標形と代替到達形を分離した。

- 君ここ系のメイン進行は `2-2 -> 7-2 -> 13-2` とする。
  - 7コスト矢澤にこ等で追加2コストが登場する `7-2-2` / `13-2-2` は上振れ代替として扱う。
- 5軸ミラステのT2目標は、主目標 `2-5-2` と、Daydream Mermaidをライブセットして成功する `2-4-2` 代替を併記する。
  - エネルギーブーストは、Daydream Mermaid系ライブをそのターンにライブセットした場合だけ有効化する。
- 10軸ミラステのT3目標は、主目標 `2-10-2` に対し、`2-11-2` / `2-13-2` などの上振れ到達を達成扱いにする。
- 各ターン、ライブカードが手札にある場合はライブセットし、ライブセット時1ドローをメンバー計画前に行う。
- レポートに `target turns` と `accepted targets` を分けて表示し、何を主目標とし、何を代替達成扱いにしたか確認できるようにした。

### 試行モデル補正 20260729d

存在しないコスト帯を目標にしないよう、目標生成を実デッキ内容基準へ変更した。

- 進行候補一覧では、デッキ内に存在しないメンバーコストを要求するテンプレートを除外する。
- 試行の各ターン目標は、実際のデッキに含まれるメンバーカードだけから作る。
- 4ターン目以降は、テンプレート上の固定コストではなく、実デッキ内の15コスト以上または最高コスト帯から動的に目標を作る。
- バトンタッチ、追加登場、コスト軽減などで到達可能と見る場合も、最終到達カード名と到達経路をレポートへ出す。
- レポートに `Target Cards And Routes` と `Decision Policy` を追加し、目標カード、候補経路、マリガンから1ターン目までの選択基準を確認できるようにした。

### 試行モデル補正 20260729e

マリガン、ライブセット、配置優先順位を見直した。

- マリガンはT1〜T3の達成率最大化を目標にする。
  - 3枚採用の10コストなど、T3目標に必要で採用枚数が少ないカードは初手にあれば残しやすくする。
  - 2コストのように採用枚数が多く引き直し期待が高いカードは、近いターンの必要枚数を超えた分を戻しやすくする。
- ライブセットはライブカード1枚固定ではなく、最大3枚の手札交換として扱う。
  - 非ライブカードも交換対象にする。
  - 直近目標に不要で、後続目標にも薄いカードを優先して交換する。
  - Daydream Mermaid系のエネルギーブーストカードは、必要ターンまでは交換せず、`2-4-2` 代替ルートを狙うターンにのみ優先してセットする。
- 配置優先順位は、ターンの目標予算内で「目標より大きいカード > 目標ぴったり > 最大の妥協札」とする。
  - 予算制限なしに大きいカードを置くとT1で13/20コストを置く不自然な結果になるため、各ターンの目標総コストと残りスロットを壊さない範囲に限定する。
- 君ここ系のT4主目標を `13-7-2` に変更し、手札が多い場合のNS三神系上振れを `13-20-2` 代替として扱う。

制限:

- 現時点ではまだ実engine連動ではなく、ステージ継続、バトンタッチ元、控え室形成、ライブ成功率、必要ハート計算を厳密には再現していない。
- 特に10軸のT3到達率は、既存ステージから一部更新する実プレイより低く出る可能性がある。

### 試行モデル補正 20260729f

ステージを維持しない試行結果は実プレイと乖離しすぎるため、最優先基盤としてステージ継続モデルを追加した。

- 試行中に3枠のステージを保持する。
- 各ターン、既存ステージのうち目標形に近いカードは残す。
- 空き枠、または目標形から遠い枠だけを手札から更新する。
- 更新候補は、そのターンの目標/代替目標で登場可能と見なす最大コスト以下に制限する。
  - これによりT1の `2-2` 目標で13/20コストを置くような不自然な動きを防ぐ。
- 低コスト追加登場効果は、ステージ枠数を超えない範囲で進行判定の仮想2コストとして扱う。

この変更により、以前の「毎ターン手札だけから盤面を作り直す」過大評価は無効になった。今後のオートプレイ精度改善は、このステージ継続モデルを土台に、バトンタッチ、控え室形成、ライブ成功率、必要ハート、実engine選択へ順次接続する。

### 試行モデル補正 20260729g

ステージ継続モデルの初期実装で、低コストの妥協札を維持しすぎる問題を修正した。

- 旧挙動:
  - T2に `4-2-2` を作った後、T3目標が `2-10-2` / `2-11-2` になっても、4コストを高コスト目標の妥協札として保持していた。
  - その結果、手札に10/11/13コストを引いていてもステージ更新候補に出にくく、T3到達率が異常に低く出た。
- 新挙動:
  - 目標より低いカードは「一時的な妥協札」として扱い、次ターン以降により高い目標カードを引いた場合は置き換え候補にする。
  - 目標以上または目標ぴったりのカードだけを強く維持する。
- 10軸のT1目標は `2-2` だけでなく、T2 `2-4-2` へ接続できる `4` も代替目標に含める。
- レポートに `Miss Reasons` を追加し、各ターン未達時に不足した主要コストを確認できるようにした。

## DB更新: プレビューカード探索要件

プレビューカードはほぼ毎日更新されるため、探索は以下を満たす必要がある。

- WIKIWIKIの `公式ポスト` 集約ページを確認する。
- 起動時更新でも古すぎる集約ページキャッシュを使い続けない。
- 集約ページにあるがローカルDBへ入っていないカードをログに出す。
- `official_preview_image_manifest.json` にあるが `preview_card_images/` に画像がないカードは、次回画像取得ターゲットに戻す。

20260729時点の対応:

- 起動時更新の `--preview-index-cache-minutes` を `360` から `15` に短縮。
- 更新スクリプト側の既定値も `30` から `15` に短縮。
- `llocg_build_preview_manifest_from_x.py` で `[PREVIEW-INDEX-MISSING-DB]` ログを出し、公式ポスト側にはあるがローカルDBにないカードを確認できるようにした。

## Stage 1補正: ターン別達成率とライブスコア目標 20260729

ターン別達成率の見え方とライブスコア目標を整理した。

- `hit_rate` は、そのターン単独で現在のステージ形が目標を満たしているかを見る補助値。
- `cumulative` は、T1からそのターンまでの目標を連続して達成できた率。進行モデルの主評価はこの値を見る。
- 君ここ系でT4単独値がT3単独値より高くなるケースは、T3を外した後にT4の形だけ戻した試行が含まれるため。これは進行達成としては `cumulative` で弾かれる。
- 君ここ系のT4主目標は `13-7-2`、NS三神による上振れ代替は `13-20-2` として明示する。
- 5軸のT4は理想 `15-5-2` / `15-4-2`、妥協 `15-2-2` を受け入れ目標として扱う。
- ライブスコア目標をデッキ内の実ライブカードから推論する。T1は最低の正スコア、T2は次段階、T3以降は最大スコアを目標にする。
- ライブスコア達成判定は、効果処理用ライブとは分け、ライブセット交換で選ばれたライブカードのうち最大スコアのものを基準にする。

### 根本原因と構造改善 20260729

問題の根本原因は、ターン目標が複数の形で別々に管理されていたこと。

- `target_turns`: レポートに表示する主目標。
- `target_alternatives`: 実際の受け入れ目標。
- `target_goal_summary`: カード名と到達経路の表示用。
- `turn_success`: 試行中の判定用。

これらを別々に後処理していたため、5軸T4のように「判定は `15-5-2 / 15-4-2 / 15-2-2` だが、表示上の主目標は `2-15-2` のまま」という不整合が起きた。また、T4単独達成率を主評価のように読める表示だったため、T3未達からT4だけ戻した試行が進行成功に見える問題もあった。

再発防止として、ターンごとの評価単位を `stage_goal_plans` に統合した。

- `seed_shape`: 進行テンプレートやデッキ推論から出た元の形。
- `primary_shape`: レポートで主目標として表示する実評価の第一候補。
- `accepted_shapes`: 実際に成功扱いする全候補。

今後は、表示・判定・目標カード表示・マリガン/ライブセット参照をこの計画データから生成する。主目標だけの差し替えや、表示専用リストへの個別パッチは禁止する。

ライブスコア目標についても、レポート専用ではなくライブセット交換へ渡し、該当ターンのスコア目標を満たすライブを優先候補にする。レポートでは以下を分けて表示する。

- 盤面 `hit_rate`: そのターン単独の盤面形達成率。
- 盤面 `cumulative`: T1からそのターンまで盤面目標を連続達成した率。
- ライブスコア `hit_rate`: そのターン単独のライブスコア目標達成率。
- ライブスコア `cumulative`: T1からそのターンまでライブスコア目標を連続達成した率。
- `combined_cumulative`: 盤面目標とライブスコア目標の両方をT1から連続達成した率。

## Stage 2: 目標補正モデル

### 目標プリセット

初期プリセットは以下。

- `turn_live_card_success`: nターン目に特定ライブカードを成功
- `turn_live_score_success`: nターン目に合計スコアi以上のライブを成功
- `turn_member_cost_play`: nターン目にxコストメンバーをプレイ
- `turn_stage_cost_shape`: nターン目のステージコストをa-b-cにする

### 目標データ案

```json
{
  "goal_id": "goal_001",
  "type": "turn_live_card_success",
  "turn": 3,
  "weight": 1.0,
  "params": {
    "card_no": "PL!-bp5-011"
  }
}
```

### 補正方針

- 目標ごとに評価関数を用意する。
- 複数目標は重み付き合計で扱う。
- 汎用テンプレートの評価値に、目標達成へ向かう補正点を加える。
- 目標に直接関わるカードやコスト帯を優先するが、カード番号専用分岐は増やさない。

## Stage 3: 繰り返し試行と構築改変探索

### 試行ログ案

```json
{
  "run_id": "autoplay_20260729_001",
  "deck_path": "user_data/decks/deck_sample.tsv",
  "model": "stage2_weighted_goals",
  "trials": 100,
  "goals": [],
  "results": {
    "goal_001": {
      "success_count": 64,
      "success_rate": 0.64
    }
  }
}
```

### 改変候補案

- 達成率の低い目標に対して、不足しているコスト帯、ライブスコア帯、特定条件の枚数を推定する。
- 入れ替え候補は「増やしたいカード群」と「削りやすいカード群」を分けて提示する。
- 実際にデッキを改変して再試行し、達成率差分を記録する。
- ユーザーへ提示する内容は、変更内容、理由、変更前後の達成率とする。

## 注意事項

- シミュレータ本体のルール処理は既存 engine を正本とする。
- オートプレイ用にルールを別実装しない。
- 効果解決が未実装または手動選択を要求する場面では、まずは安全な既定選択を記録し、後続で選択モデルを強化する。
- 自動試行結果は乱数 seed、デッキ内容、モデル設定、目標設定と一緒に保存する。
- 構築変更はユーザーの元デッキを直接上書きせず、候補デッキとして別名保存する。
